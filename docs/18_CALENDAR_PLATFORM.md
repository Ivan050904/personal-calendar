# Calendar Platform — единый календарь с API для приложений

Статус: **утверждено владельцем 2026-11-05** (решения D34–D38 в `17_DECISIONS.md`). Реализация идёт волнами (§11); каждая волна стартует отдельной командой.

## 1. Цель

Календарь становится самостоятельным сервисом со своими аккаунтами, как Google или Яндекс Календарь. Любое зарегистрированное приложение (Folio, приложение для репетиторства, будущее приложение для пар) подключается к аккаунту календаря по API с разрешения пользователя. В интерфейсе календаря пользователь видит всё вместе: каждое приложение своим цветом.

Сейчас всё иначе (D31): пользователь календаря выводится из `folio_user_id`, мост принимает только `iss == "folio"`, а сервисный токен Folio (`folio_service_token`) общий на весь сервер. Своих аккаунтов у календаря нет, и подключить второе приложение некуда.

### Входит в спецификацию
1. Аккаунты и вход в сам календарь (логин + пароль).
2. OAuth 2.0: «Войти через Календарь» и подключение приложений.
3. Несколько календарей у аккаунта и права приложений.
4. Синхронизация: внешние ID, лента изменений, webhooks.
5. Общие события между аккаунтами (нужно приложению для пар).
6. Перевод Folio со старого моста на OAuth.

### Не входит
- Новый дизайн и интерфейс календаря (отдельная задача и отдельные агенты). Здесь только какие экраны нужны, а не как они выглядят.
- Само приложение для пар и сама интеграция в репетиторском приложении: в них пишется только клиентская часть по этому контракту.
- Email: подтверждение почты, письма, сброс пароля по почте (D34).
- Защита открытой регистрации от ботов (её описание пришлёт владелец; до этого регистрация выключена, §3.2).
- Импорт из Google/Яндекс и подписка на чужие календари.

## 2. Термины

- **OAuth** (Open Authorization, «открытая авторизация») — общий стандарт, по которому одно приложение получает доступ к данным пользователя в другом сервисе, не узнавая его пароль. «Open» означает открытый стандарт, а не продукт Google. У нас роль «Google» играет Календарь.
- **Аккаунт** — пользователь календаря: логин + пароль. Заменяет `CalendarPrincipal`.
- **Клиент (приложение)** — зарегистрированное в календаре приложение: Folio, Репетитор, Пары. У него есть `client_id`, `client_secret` и разрешённые `redirect_uri`.
- **Разрешение (grant)** — запись «аккаунт A разрешил приложению X такие-то права». Её видно в настройках, и её можно отозвать.
- **Scope** — одно право внутри разрешения (например, «читать события»).
- **Календарь** — контейнер событий/задач/планов внутри аккаунта. У аккаунта их несколько.

## 3. Аккаунты и вход

### 3.1 Модель
`calendar_principals` превращается в аккаунт (таблица переименовывается или расширяется, решает волна 1):
- `id` (как сейчас), `login` (уникальный, в нижнем регистре, 3–32 символа: латиница, цифры, `_`, `.`, `-`), `password_hash`, `display_name`, `active`, `created_at`. Часовой пояс у аккаунта не хранится: он уже есть у календаря.
- `folio_user_id` и `legacy_alias` остаются только на время миграции (§8) и потом удаляются.

### 3.2 Сценарии
- **Создание аккаунта.** Пока регистрация закрыта, аккаунты создаёт владелец скриптом `backend/scripts/` (логин, имя, временный пароль). Эндпоинт регистрации `POST /api/v2/accounts` уже есть, но отвечает `503`, пока `REGISTRATION_ENABLED=false`. Включается, когда будет готова защита от ботов. При создании аккаунта сразу создаётся календарь «Личное» (как сейчас `ensure_actor_calendar`).
- **Вход:** логин + пароль → существующая сессия `calendar_sessions` (httpOnly cookie). Заменяет одиночный вход из env (D17).
- **Выход и «выйти на всех других устройствах»** (`POST /api/v2/me/sessions/revoke-others`): через `revoked_at`, который уже есть. Список сессий — позже, вместе с экранами настроек.
- Управлять аккаунтом (пароль, сессии) можно только из сессии в интерфейсе календаря, не токеном приложения.
- **Смена пароля** (нужен текущий пароль): отзывает все сессии, кроме текущей. Разрешения приложений остаются: они не зависят от пароля и отзываются отдельно (§5.4).
- **Забыл пароль:** почты нет, поэтому новый временный пароль выдаёт владелец скриптом. Скрипт отзывает все сессии аккаунта.

### 3.3 Безопасность входа
- Пароль хранится как хеш Argon2id. Зависимость `argon2-cffi`: в проекте нет библиотеки хеширования паролей, а писать хеширование вручную нельзя. Минимальная длина пароля 8 символов.
- Ограничение попыток входа по логину и по IP (в памяти процесса, одного инстанса API достаточно, D18).
- Ответы на «нет такого логина» и «неверный пароль» одинаковые.

## 4. OAuth: подключение приложения

### 4.1 Поток (Authorization Code + PKCE)
На примере репетиторского приложения:

1. В приложении пользователь жмёт «Подключить календарь».
2. Приложение перенаправляет браузер на `GET /oauth/authorize?client_id=…&redirect_uri=…&scope=…&state=…&code_challenge=…&code_challenge_method=S256`.
3. Календарь просит войти в аккаунт календаря, если сессии нет.
4. Экран согласия: «Приложение „Репетитор“ хочет: видеть ваши события; создавать события в календаре „Репетитор“. [Разрешить] [Отмена]». Если запрошено чтение, пользователь здесь же выбирает, какие календари приложение видит (§5.3).
5. Календарь возвращает браузер на `redirect_uri?code=…&state=…`. Код одноразовый и живёт 60 секунд.
6. Сервер приложения вызывает `POST /oauth/token` (code + code_verifier + client_id + client_secret) и получает `access_token` и `refresh_token`.
7. Приложение хранит токены у себя, привязав их к своему пользователю. Связь «пользователь репетиторки ↔ аккаунт календаря» существует только в виде этих токенов, и ID между сервисами не передаются.
8. Дальше приложение ходит в `/api/v2/*` с заголовком `Authorization: Bearer <access_token>`.

Если разрешение уже выдано с теми же scope, экран согласия повторно не показывается.

### 4.2 «Войти через Календарь»
Тот же поток плюс scope `openid profile`. Приложение получает ID аккаунта календаря, логин и имя и может по ним завести у себя пользователя. Так в приложение для пар можно будет входить календарным аккаунтом.

Вход в приложение и подключение календаря — разные вещи: можно подключить календарь, не входя через него, и наоборот (тогда приложение просит только `openid profile`).

### 4.3 Токены
- `access_token`: случайная строка, 15 минут; в БД хранится только хеш.
- `refresh_token`: 30 дней, при каждом использовании выдаётся новый, а старый гаснет. Повторное использование погашенного токена отзывает всё разрешение (признак кражи).
- `POST /oauth/revoke` — приложение само отключается.
- Отзыв в настройках календаря мгновенно гасит все токены этого разрешения.

### 4.4 Какие приложения могут подключиться
Только зарегистрированные. Приложение, которого нет в `oauth_clients`, получит ошибку ещё до экрана входа. Зарегистрированное приложение тоже ничего не видит, пока конкретный пользователь не нажмёт «Разрешить», и видит только свой аккаунт.

Клиентов создаёт владелец скриптом в `backend/scripts/` (name, redirect_uris, разрешённые scope, тип: серверное или публичное). `client_secret` показывается один раз, в БД хранится хеш. Самостоятельная регистрация сторонними разработчиками — не в этой спецификации.

Публичные клиенты (мобильное приложение без сервера) секрета не имеют. PKCE обязателен для всех клиентов.

### 4.5 Требования безопасности OAuth
- `redirect_uri` проверяется точным совпадением со списком клиента.
- Обязательный `state`; PKCE только `S256`; коды и токены — `secrets.token_urlsafe(32)`, в БД только SHA-256.
- Код одноразовый: повторное предъявление кода отзывает выданные по нему токены.
- Экран согласия нельзя встроить в iframe (`frame-ancestors 'none'`); кнопка «Разрешить» — POST с CSRF-защитой.
- Приложение никогда не получает cookie календаря.
- Запросы к API с Bearer-токеном не проверяются на Origin (как сейчас для моста), а запросы с cookie проверяются.
- Ограничение частоты на `/oauth/token`.

### 4.6 Реализация
OAuth-сервер пишется в проекте вручную (D35), без библиотеки. Причина: у `authlib` готовая серверная интеграция есть для Flask и Django, но не для FastAPI, а адаптер к ней — это тот же объём кода, только с чужой абстракцией. Эндпоинтов пять (§9), и каждое требование §4.5 закрывается отдельным тестом. После волны 3 — отдельный security review.

## 5. Календари и права приложений

### 5.1 Несколько календарей
У аккаунта:
- **«Личное»** — создаётся вместе с аккаунтом, принадлежит пользователю.
- **Календарь приложения** — создаётся автоматически при первом подключении приложения с правом записи: «Репетитор», «Folio». Помечен `source_client_id`.
- **Свои дополнительные календари** — пользователь создаёт сам («Работа», «Спорт»).

У каждого календаря есть цвет и флаг «показывать в общем виде». **Общий вид** в интерфейсе накладывает все видимые календари друг на друга: дела из Folio одним цветом, уроки из репетиторки другим, личные третьим.

`calendars` получает поля `kind` (`personal` | `app` | `user`), `source_client_id`, `color`, `visible`, `sort_order`. Поле `default_owner` остаётся признаком календаря «Личное».

### 5.2 Scopes
| Scope | Что даёт |
|---|---|
| `openid profile` | ID, логин и имя аккаунта (только «Войти через Календарь») |
| `calendars.read` | видеть список календарей, выбранных на экране согласия |
| `events.read` | читать события/задачи/планы в выбранных календарях |
| `events.write` | создавать, менять и удалять **только в своём календаре приложения** |
| `freebusy.read` | видеть «занят/свободен» по всем календарям без названий событий |
| `sharing.invite` | приглашать другие аккаунты на события (§7) |

Существующие scope моста (`calendar:read`, `calendar:write` …) сопоставляются с новыми при миграции Folio (§8).

### 5.3 Правила доступа
- Приложение пишет только в свой календарь приложения, в «Личное» и чужие календари — нет. Именно поэтому у каждого приложения свой цвет, и видно, откуда пришло событие.
- Приложение читает только календари, которые пользователь отметил на экране согласия. По умолчанию отмечен его собственный календарь.
- Пользователь в интерфейсе может редактировать события в календаре приложения; приложение узнает об этом через ленту изменений (§6).
- Удаление календаря приложения пользователем отзывает право записи этого приложения.
- Отзыв разрешения не удаляет календарь приложения: пользователь решает, удалить его или оставить как обычный.

### 5.4 Экран «Подключённые приложения»
В настройках календаря: список разрешений (приложение, права, какие календари видит, когда подключено, когда последний раз обращалось) и кнопка «Отключить».

## 6. Синхронизация

### 6.1 Внешние ID
У события/задачи/плана появляется пара `(source_client_id, external_id)`, уникальная в пределах календаря. Приложение передаёт свой ID («урок №123»), и повторная отправка того же урока обновляет событие, а не создаёт дубль. Существующие `Idempotency-Key` и `revision` (конфликт при устаревшей версии) остаются.

### 6.2 Лента изменений
`GET /api/v2/changes?cursor=…` — уже существующая `calendar_changes`, но:
- курсор хранится на стороне приложения;
- фильтруется по календарям, видимым этому разрешению;
- в записи есть `actor`: кто изменил (пользователь в интерфейсе, приложение X, приглашение), чтобы приложение не реагировало на собственные правки.

### 6.3 Webhooks
Приложение может зарегистрировать URL: `POST /api/v2/webhooks`. При изменении календарь шлёт короткое уведомление «есть изменения, курсор такой-то» с подписью HMAC-SHA256 в заголовке, а за данными приложение идёт в ленту. Неудачная доставка повторяется с паузами до 24 часов. Webhook — подсказка, источник правды — лента.

## 7. Общие события между аккаунтами (для приложения пар)

Минимум, который нужен паре: один создаёт событие, оно появляется у обоих, и у каждого видно, принял ли второй.

- У события появляются **участники** (`event_attendees`): аккаунт, статус `pending` | `accepted` | `declined`.
- Приглашать можно только существующий аккаунт календаря по логину.
- Событие живёт в календаре организатора. У приглашённого оно показывается в его общем виде (как «входящее приглашение», пока он не ответил) и попадает в его ленту изменений.
- Менять время и название может только организатор; участник меняет только свой статус.
- Приложение для пар создаёт событие от имени пользователя через `events.write` + `sharing.invite`.

Совместные календари с правом редактирования у двоих («Наш календарь») — следующий шаг после приглашений, в эту спецификацию не входят.

## 8. Перевод Folio

Сторона календаря делается в волне 5. Сторона Folio описана для агента Folio в `development/handoff/FOLIO_OAUTH_MIGRATION.md`.

1. Folio регистрируется как OAuth-клиент.
2. У существующих пользователей календаря, созданных через Folio, нет логина и пароля. При следующем входе из Folio старый launch-exchange (`/auth/folio`) пускает их как сейчас и просит задать логин и пароль: аккаунт тот же, данные не переносятся.
3. После этого Folio проходит обычное подключение (§4.1) и переходит на `/api/v2` с токенами разрешения.
4. Общий сервисный токен Folio и HMAC-мост (D31) отключаются, когда в Folio не остаётся пользователей на старой схеме. До этого они работают параллельно.
5. Личный аккаунт владельца (`legacy_alias`, вход из env) превращается в обычный аккаунт с логином и паролем.

## 9. API v2 (набросок)

Новый префикс `/api/v2`, общий для интерфейса календаря и приложений. Существующий `/integration/v1` живёт до конца миграции Folio.

- `POST /accounts` (за флагом), `GET /me`, `POST /me/password`, `POST /me/sessions/revoke-others` — сделано в волне 1
- `GET /calendars`, `POST /calendars`, `PATCH /calendars/{id}`, `DELETE /calendars/{id}`
- `GET /events?calendar_id=&from=&to=` (развёрнутые повторы, как текущие occurrences), `GET /events/{id}`
- `POST /events`, `PATCH /events/{id}`, `DELETE /events/{id}` с `external_id`, `Idempotency-Key`, `If-Match: <revision>`
- то же для `tasks` и `plans`
- `GET /freebusy?from=&to=`
- `GET /changes?cursor=`
- `POST /events/{id}/attendees`, `PATCH /events/{id}/attendees/me`
- `POST /webhooks`, `DELETE /webhooks/{id}`
- `GET /grants`, `DELETE /grants/{id}` (экран «Подключённые приложения»)

OAuth-эндпоинты вне `/api/v2`: `/oauth/authorize`, `/oauth/token`, `/oauth/revoke`, `/oauth/userinfo`, `/.well-known/oauth-authorization-server`.

Точная схема запросов и ответов пишется в волне 3 в `04_API_CONTRACT.md`.

## 10. Новые таблицы

- `oauth_clients` — id, name, secret_hash, type, redirect_uris, allowed_scopes, active.
- `oauth_authorization_codes` — code_hash, client, account, scopes, redirect_uri, code_challenge, expires_at, used_at.
- `oauth_grants` — account, client, scopes, readable_calendar_ids, created_at, revoked_at, last_used_at.
- `oauth_tokens` — grant, type (access/refresh), token_hash, expires_at, revoked_at, replaced_by.
- `event_attendees` — event, account, status, responded_at.
- `webhook_subscriptions` — grant, url, secret_hash, active, failures.
- Поля аккаунта (§3.1), поля `calendars` (§5.1), `external_id`/`source_client_id` у событий, задач и планов, `actor` в `calendar_changes`.

Все изменения — через Alembic, линейной цепочкой после текущих ревизий.

## 11. Волны

Каждая волна заканчивается своим тест-планом и regression check по `development/QUALITY_GATE.md`; к следующей волне автоматически не переходим.

1. **Аккаунты и вход.** Логин/пароль, Argon2id, сессии, «Личное» при создании, скрипты владельца (создать аккаунт, сбросить пароль), регистрация за флагом. Тесты: создание, повторный логин, вход и неверный пароль, лимит попыток, смена пароля отзывает сессии, флаг выключен → 503, изоляция данных двух аккаунтов.
2. **Несколько календарей.** CRUD календарей, цвет/видимость, общий вид в текущем интерфейсе (минимально, без редизайна). Тесты: события в разных календарях, чужой календарь → 404.
3. **OAuth-сервер и API v2.** authorize/token/revoke/userinfo, экран согласия, scopes, календарь приложения, чтение/запись v2, скрипт регистрации клиентов. Тесты: весь поток с PKCE, незарегистрированный клиент, неверный redirect_uri, повтор кода, ротация и повторное использование refresh, запись вне своего календаря → 403, чтение невыбранного календаря → 404.
4. **Синхронизация.** external_id, лента по разрешению с actor, webhooks с подписью и повторами. Тесты: повторная отправка без дублей, конфликт ревизий, лента не отдаёт невидимые календари.
5. **Перевод Folio.** Задание логина/пароля для Folio-аккаунтов, Folio как OAuth-клиент, параллельная работа старого моста. Тесты: старый и новый путь на одних данных; после отключения моста старые токены → 401.
6. **Приглашения.** Участники, статусы, показ у приглашённого. Тесты: организатор меняет время, участник видит; участник не может менять событие; приглашение несуществующего логина → ошибка.
