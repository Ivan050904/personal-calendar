# Handoff для агента Folio: переход на OAuth календаря

Отправитель: проект Personal Calendar (`calendar.folio-one.ru`). Дата: 2026-11-05.
Основание: `docs/18_CALENDAR_PLATFORM.md` (§4, §8) и решения D34–D38 в `docs/17_DECISIONS.md` календаря.

## ⚠ Когда начинать

**Не раньше, чем календарь сообщит, что на проде готовы волна 3 (OAuth + API v2) и волна 5 (перевод Folio).** До этого в Folio ничего не меняется: текущая интеграция (мост с подписанным JWT, launch-exchange `/calendar/sso/exchange`, сервисный токен `CALENDAR_SERVICE_TOKEN`) продолжает работать. Точную схему запросов `/api/v2` календарь допишет в свой `docs/04_API_CONTRACT.md` в волне 3: сверяйся с ней, а не с этим файлом, если они расходятся.

## Что меняется по сути

Сейчас календарь узнаёт пользователя по `folio_user_id` из JWT, который подписывает Folio общим секретом. После перехода у календаря свои аккаунты (логин + пароль), а Folio — одно из подключённых приложений, как любое другое. Folio хранит для каждого своего пользователя токены доступа к его аккаунту календаря.

## Что нужно сделать в Folio

1. **Получить данные клиента.** Владелец создаст клиента скриптом календаря и передаст `client_id`, `client_secret` и согласованный `redirect_uri` (например, `https://folio-one.ru/calendar/oauth/callback`). Секрет хранить только в env сервера Folio, в git не коммитить.
2. **Кнопка «Подключить календарь».** На сервере Folio:
   - сгенерировать `state` и `code_verifier` (43–128 символов), сохранить их в сессии пользователя;
   - `code_challenge = BASE64URL(SHA256(code_verifier))`;
   - редирект на `https://calendar.folio-one.ru/api/oauth/authorize?response_type=code&client_id=…&redirect_uri=…&scope=calendars.read events.read events.write&state=…&code_challenge=…&code_challenge_method=S256`.
3. **Callback.** Проверить `state`. Затем серверный `POST https://calendar.folio-one.ru/api/oauth/token` с `grant_type=authorization_code`, `code`, `redirect_uri`, `client_id`, `client_secret`, `code_verifier`. Получить `access_token` (15 мин) и `refresh_token` (30 дней).
4. **Хранение.** Новая таблица в Folio: пользователь Folio → `refresh_token` (зашифрованный или как минимум не логируемый), `access_token` + срок, выбранные scope, время подключения. На одного пользователя Folio — одно подключение.
5. **Обновление токена.** Перед запросом, если `access_token` истёк: `POST /api/oauth/token` с `grant_type=refresh_token`. **Каждый раз сохранять новый refresh_token**: старый гаснет, а повторная попытка его использовать отзывает всё подключение. Два параллельных обновления для одного пользователя не допускать (блокировка на пользователя).
6. **Запросы.** Всё, что Folio делает через `/integration/v1` сейчас, есть в `/api/v2`:
   - `agenda`, `occurrences`, `confirmations`, `history`, `reminder-source`;
   - CRUD для `events` / `tasks` / `plans`;
   - действия `…/{id}/confirm|complete|restore` вместо `operation` в командах.

   Таблица соответствия — в `docs/04_API_CONTRACT.md` календаря, раздел Events v2. Все обращения к календарю идут в `/api/v2/*` с `Authorization: Bearer <access_token>` вместо JWT-моста и вместо `CALENDAR_SERVICE_TOKEN`. Ответ `401` означает, что токен протух или подключение отозвано: один раз обновить токен, затем показать пользователю «Подключите календарь заново».
7. **Свой календарь.** Folio пишет только в календарь приложения «Folio» (он создаётся сам при первом подключении). Старые записи Folio остаются в «Личном» пользователя. Если на экране согласия отмечено «Личное», Folio их видит, но менять не может (403): так решил владелец (D39). Показывать их в Folio только для чтения. При создании событий передавать `external_id` (ID сущности в Folio) и `Idempotency-Key`. Чтобы видеть изменения, использовать `GET /api/v2/changes?cursor=…` и хранить курсор у себя. Свои же правки отсеиваются по `actor` (`app:<client_id>` Folio). Повторный POST с тем же `external_id` обновляет событие, а не создаёт дубль; если пользователь событие удалил, придёт 409 с `deleted: true`. Webhook (`POST /api/v2/webhooks`) — только подсказка «иди в ленту», проверять подпись `X-Calendar-Signature`.
8. **Отключение.** Кнопка «Отключить календарь» в Folio вызывает `POST /api/oauth/revoke` и удаляет токены у себя. Пользователь может отключить Folio и со стороны календаря, тогда Folio получит `401` (см. п. 6).
9. **Логин и пароль у старых пользователей.** У аккаунтов календаря, созданных через Folio, нет логина. Перед подключением по OAuth пользователь задаёт его в календаре: «Настройки → Логин и пароль». Folio может открыть календарь через старый `/auth/folio` и попросить сделать это.
10. **Переходный период.** Пользователи, которые ещё не подключились по-новому, продолжают работать через старый мост. Новый путь включать под флагом. Когда у всех активных пользователей есть подключение, сообщить владельцу: календарь выключит мост и сервисный токен, после чего удалить старый код в Folio.

## Что НЕ делать

- Не передавать в календарь пароли пользователей и не просить их.
- Не хранить `client_secret`, `refresh_token`, `access_token` в логах, git и на фронтенде (браузер Folio токенов календаря не видит).
- Не выключать старый мост в Folio, пока календарь не подтвердит отключение со своей стороны.

## Проверка, что всё работает

- Новый пользователь Folio: подключение → экран согласия календаря → возврат в Folio → события из Folio появляются в календаре цветом «Folio».
- Повторная отправка той же сущности не создаёт дубль.
- Отзыв подключения в настройках календаря → Folio показывает «Подключите заново».
- Через 16 минут после подключения запросы идут (токен обновился сам).
- Пользователь на старой схеме продолжает работать до своего переподключения.
